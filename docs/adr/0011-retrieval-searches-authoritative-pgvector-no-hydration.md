# Retrieval searches the authoritative pgvector store directly — there is no hydration step

The retrieval pipeline is **scope → (refine) → embed → search → package**. It has no "hydrate and validate the hits against a system of record" stage, and it does not overfetch-then-filter. Every filter — the mandatory `patient_id`, an optional `doctor_id`, and optional `document_type` / clinical-date / `session_id` narrowing — is applied in the same SQL `WHERE` clause as the vector search, and the ANN scan returns exactly the requested `TopK` already validated.

Why: the design this is adapted from keeps embeddings in a separate vector engine (Weaviate / Azure AI Search) and the authoritative document/version/chunk records in SQL. There, a vector hit is a *candidate* that may be stale or orphaned, so it must be re-loaded and re-validated against SQL before it can be trusted, and the search overfetches to survive that filtering. This service has no such split: pgvector **is** the SQL store (ADR-0001). A `chunks` row already holds the embedding, the verbatim text, and the full metadata spine (patient, doctor, document id/type, clinical date, source location) in one Postgres row, and it is written and deleted atomically with its document (ADR-0003). A search hit is therefore already the authoritative record — there is nothing to hydrate it from and nothing to reconcile it against.

## Consequences

- **`patient_id` is the security boundary, enforced in the query, not by a post-filter.** A retrieval that does not constrain `patient_id` is a bug, not a slow path. This is the same filter the store already relies on and the reason the `chunks` B-tree on `(patient_id, doctor_id)` exists (ADR-0001) — it serves the retrieval filter directly.
- **The ANN query must match the index cast.** Search orders by `embedding::halfvec(3072) <=> query::halfvec(3072)` so it uses the HNSW index built over the `halfvec` cast; ordering by the raw `vector(3072)` would silently table-scan. The query embedding is produced by the **same model and dimensions as ingestion** (`text-embedding-3-large`, 3072); `Chunk.EmbeddingModel` records what produced each vector so a model change is a managed re-embedding, never a silent mismatch.
- **No overfetch multiplier, no reconciliation job.** Because filtering is authoritative and in-query, `TopK` is requested directly. There is no candidate-vs-record drift to sweep, so no reconciliation machinery is carried.
- **A future second source (e.g. structured analyte trends) does not change this.** If structured claims are added later, they arrive as a *separate* retrieval source with their own explicit merge and ranking policy — they are not folded into this vector search, and they do not reintroduce a hydration step for chunks.
- **Do not "add hydration for safety."** A reader who knows the two-store RAG pattern may expect a validation pass and try to add one. There is no second store to validate against; adding one would only duplicate the row the search already returned.
