# Grounded chat verifies before releasing an answer and refuses when the record has no evidence

The chat answer is generated prose — which inverts the ingestion invariant, where no generative model ever produces a stored word of patient text (ADR-0002/0006). For chat, the model *does* write the words, so the invariant is restated rather than dropped: **the model may only assert what the retrieved evidence supports, and the service proves that before the answer leaves it.** Three rules make that concrete in v1:

1. **Confidence threshold.** A vector hit below a configured similarity floor is not treated as evidence. "The search returned something" is not "the record supports this."
2. **Insufficient-evidence refusal.** When nothing clears the threshold, the assistant returns an explicit *insufficient evidence* answer — "this patient's record does not contain information to answer that" — instead of answering from the model's own general medical knowledge.
3. **Citation verification.** Every `[E#]` reference the answer makes must point at an evidence item that was actually supplied to the model on this turn, and each cited chunk must still resolve. The answer is generated in full, verified, and only then returned. Nothing ungrounded is ever emitted. **Verification failure fails the turn (5xx) with no corrective retry** — deliberately unlike ingestion's single corrective chunking retry: a stray citation is not worth a second generation, and failing fast keeps the safety-critical path simple and lets the caller decide whether to retry.

Because verification runs on the *complete* answer, v1 is **non-streaming**: generate → verify → return. There is no live token stream that could surface an ungrounded claim before the citation check rejects it — and there is no live consumer to serve one anyway, since conversations and the app channel live in the backend (ADR-0010).

Why: the corpus is a **single patient's own record** — transcripts, notes, lab renditions, imaging findings — not a library of clinical literature. So the medical risk here is not "which source is authoritative" (there is one tier: the patient's real documents); it is answering a clinical question the record does not actually support. Grounding, refusal, and verification address exactly that. Streaming is a UX optimisation whose only failure mode is showing unverified medical text early — a cost with no matching v1 benefit.

## Consequences

- **Grounding rules are unconditional.** With one fixed clinical voice and no persona in v1, there is no presentation layer that could soften or override the evidence rules. What the reference design frames as "personas must not weaken grounding" becomes simply: the rules always apply.
- **Refusal is a normal, successful outcome.** An insufficient-evidence answer is a `200` with a refusal payload and zero citations, not an error. Its text is **deterministic and code-owned**, selected by the question's language (el/en) — no model call runs on the refusal path, so the model can never "helpfully" answer from general knowledge once we've decided there is nothing to ground. A patient with no chunks at all (unknown or empty record) takes this same path — a refusal, not a `404`, so patient existence is not leaked and no patient registry is assumed. It is a first-class result the golden set (T36) asserts on.
- **The threshold is config, calibrated against the golden set.** The similarity floor is not hard-coded lore; it is tuned against curated Greek/English/mixed cases (T36) so refusal fires when — and only when — it should. Retrieval, embedding, and generation failures still fail the turn after retries; refinement fails open to the raw question.
- **Source authority and freshness are reframed, not implemented.** No source-authority hierarchy (single-patient corpus); "freshness" is the clinical `DocumentDate` already on every chunk, surfaced so the doctor sees *when*, not used to expire evidence. Hybrid lexical search for exact drug names / codes is a deferred recall improvement, not a grounding rule.
- **Telemetry, not stored text, is the record of a turn.** Extending ADR-0009, chat emits spans (refine / embed / search / generate / verify), and metrics (answered vs. refused, citation count, latency) carrying only ids and counts — never the question or answer text. No chat rows are persisted here (ADR-0010).
- **Answer language follows the question; retrieval is cross-language.** Multilingual embeddings match a Greek question to English chunks and vice versa, so grounding never fails for language reasons; the answer is written in the language the doctor asked in, citing evidence whatever language it is in.
