# Retrieval and grounded answering live in this service; conversation state lives in the backend

This service gains two new capabilities — a patient-scoped **retrieval** endpoint that returns ranked verbatim evidence, and a stateless **grounded-answer** endpoint that turns a question plus that evidence into a cited clinical answer. It does **not** gain conversations. Persisting messages, idempotency keys, conversation memory (recent turns + a rolling conversation summary), and auto-titles all belong to the existing backend, which is the one caller (ADR-0007) and the only component with a user identity and a channel to the doctor's app. The grounded-answer endpoint *accepts* bounded conversation context as request input so it can resolve pronouns and stay multi-turn-ready, but it **stores none of it**.

Why: the reference design this is adapted from (Consultant-AI) is a single service that owns retrieval, generation, *and* the whole conversation lifecycle. Copying that here would rebuild message tables, idempotency, and memory that the backend already has the identity and the app-facing channel to own — and it would widen a boundary ADR-0007 deliberately kept narrow. Keeping this service stateless about chat means it does exactly one new thing well (find evidence and ground an answer in it) and remains a pure function of its inputs: same patient, same question, same evidence in — same answer out, no hidden conversation state to reason about.

## Consequences

- **The grounded-answer contract carries conversation context as input, never as stored state.** `{ patientId, doctorId, question, recentTurns?, priorSummary? }` in; a cited answer out. The backend supplies memory when it exists; until then the fields are simply omitted and the endpoint answers single-turn. Adding real multi-turn later is a caller change, not a schema change here.
- **Conversation memory is never an evidence source.** Recent turns and any prior summary are used only to interpret the question (pronouns, references) and to phrase the answer. Every medical fact in an answer is re-retrieved and grounded on the current turn — a remembered sentence is never promoted to fact. This is the memory-isolation rule the medical adaptations call for.
- **This service still has no user identity.** As with ingestion, `doctorId`/`patientId` travel in the payload and are trusted from the backend. The who-asked-what user audit is the backend's, because only the backend knows the user.
- **The boundary in ADR-0007 is extended, not breached.** There is still exactly one caller and still no per-user token here. If a second caller or public exposure ever appears, ADR-0007 remains the first thing to revisit.
- **Streaming is the backend's concern to relay.** Because conversations and the app channel live in the backend, this service returns a complete answer (see ADR-0012); live token streaming to the app, if wanted, is added at the backend's SignalR channel, not invented here.
