# Observability is OpenTelemetry plus a persisted per-ingestion quality report

The service explains itself two ways. Operationally, it emits OpenTelemetry from one `ActivitySource`/`Meter` named `MedicalAssistance.Ingestion`: distributed traces (ASP.NET Core requests, HttpClient calls, Npgsql database commands, and a span around every agent, embedding and extraction call), outcome-and-duration metrics per ingestion, and structured logs scoped to the ingestion id for the length of a run. Where the signals go is not the code's business — the OTLP exporter is added only when `OTEL_EXPORTER_OTLP_ENDPOINT` is configured, so a deployment turns telemetry on with one environment variable while local runs and the test host open no exporter connections.

Separately, and durably, each completed ingestion writes an `ingestion_quality_reports` row in the *same transaction* as its chunks: chunk count, the per-chunk token distribution, how many sub-floor fragments the guardrails merged and over-ceiling chunks they split, and whether the chunking agent's one corrective retry fired. It is read at `GET /ingestions/{id}/quality`.

Why: the PRD's "the system explains itself" constraint has two audiences. An operator asking "why is this slow or failing?" needs live traces and metrics, and OpenTelemetry is the vendor-neutral way to give them that without binding the service to one backend. But a *chunking-quality* regression is invisible to traces — it is a change in the shape of what was stored, seen only by comparing many documents against a baseline. Persisting the quality report at commit time is what turns a golden set (T36) from an assertion into a measurement: a rise in the guardrail counts or the retry rate across a fixed corpus is a regression *seen*, not suspected.

## Consequences

- **Telemetry carries no patient content.** Spans and metrics record ids and counts only — an ingestion id, a document type, a chunk count, a byte size — never a word of a transcript or a rendered panel. This is the same boundary the store enforces (ADR-0002/0006), extended to everything that leaves the process as telemetry: a span says *how many* chunks were embedded, never *what* they said.
- **The quality report is atomic with the chunks it describes** (ADR-0003). A completed ingestion always has a report, and a report never describes a run that did not finish — so `GET /ingestions/{id}/quality` is 404 for anything unknown, still running, or failed before it committed. The report row is keyed by and foreign-keyed to the ingestion, so erasure and rerun remove it by cascade rather than leaving an orphan.
- **The guardrail counts and the retry flag are measured, not modelled.** They are recorded by the code that does the merging, splitting and retrying — a deterministic strategy that runs no chunking agent (a LabReport rendering panels) reports `0` merges, `0` splits and no retry, which is honest because none of those repairs was ever possible.
- **Log correlation is a scope, not a convention.** The worker opens one logging scope with the ingestion id (then the document type and patient) around each run; because scopes flow through the shared async-local provider, the pipeline, committer and summariser loggers inherit it without being handed it. `IncludeScopes` is on for both the console (local) and the OpenTelemetry log exporter.
- **Export is opt-in, so cost is opt-in.** With no OTLP endpoint configured the SDK still collects, but nothing is exported and no collector connection is attempted — the instrumentation is always present and effectively free until an environment asks for it.
